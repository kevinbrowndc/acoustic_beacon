# D07 acquisition optimization

D06 is the known-good physical-device baseline. Its APK is preserved in the project root, and its source snapshot is in `baselines/D06-source` beside this app. D06 APK SHA256: `f9c06810d906b98a71e762bb0d619aa66672485ec6a8c138521bb39c588a637d`.

## Acquisition changes

D07 retains D06's bounded observation buffer and frequency-evidence gates. Sixteen timing phases cover the 80 ms grid at 5 ms resolution. Each phase maintains a rolling 32-bit word and score; each new observation updates only the newly completed slot instead of recalculating all 32 slots. Searching begins as soon as a complete preamble window exists, without waiting for the buffer to fill.

A partial preamble prefix prioritizes promising phases. Only the exact `11010011100100011010011001011100` preamble can lock. The first exact match locks immediately, removing D06's extra 80 ms alignment-selection delay. Nearby exact matches remain bounded fallback candidates with individually fixed timing grids; the first fully valid frame wins once. They do not delay the primary candidate. Failed candidates retain observation history and rolling search state. Later preamble hits can resume acquisition without clearing useful observations.

The D05 burst trace remains diagnostic only. It does not supply decoded frames. Frequencies, 80 ms transmitted symbols, waveform format, header, payload `wookiemeat`, CRC, confidence/support gates and matching-frame validation remain unchanged. No incorrect preamble or CRC is accepted.

## Diagnostics

The existing Debug screen adds first usable signal to first lock, first lock to first CRC-valid payload, first usable signal to payload, and total time to validated matching frames. These are audio-sample times since listening started, not wall-clock processing benchmarks. The screen also reports distinct timing offsets tested, evaluations, preferred phase, best pre-lock Hamming distance, candidate failure counts, and result/failure reason. Stopping listening preserves an incomplete-frame diagnosis. Reasons describe decoder observations, not an inferred physical acoustic cause.

## Automated evidence

All 60 tests pass, including the existing waveform audit and fragmented/joined/arbitrary-offset tests. Eight new acquisition tests cover:

- Earliest full preamble: D06 locks at 2640 ms; D07 at 2560 ms, before its 2730 ms buffer fills.
- Rejected-preamble search: D06 performs 91,340 slot evaluations; D07 performs 7,297, about 92% fewer. A test-only copy of D06 counts calls without changing decoding behavior. This is a work-count comparison, not a CPU benchmark.
- Nearby exact-alignment fallback recovers delayed evidence without duplicate frame delivery.
- Eight identical actual-WAV playbacks, with an arbitrary sample offset and varied callback chunking, each recover three CRC-valid frames and the validated payload `wookiemeat`. All eight have identical audio-time latency: first lock 2515 ms, lock to first payload 8960 ms, first payload 11475 ms, validated matching frames 23495 ms.
- Four successive WAV playbacks in one listening session recover all twelve valid frames.
- Silence, insufficient observations, wrong preamble, invalid header, CRC failure, incomplete stopped frame and awaiting-repeat diagnoses.
- Failed header followed by healthy frames recovers without clearing the rolling buffer.

The matching D07 WAV is generated by the unchanged generator. Its SHA256 is `6f4d14899f12da6931283e7b1f3ffd24d48bdf7e5b299751d4eaac6216956caf`, identical to the prior test waveform. Independent audit checks 48 kHz mono PCM16, frequency mapping, silent halves and frame bytes `d3 91 a6 5c 01 0a 77 6f 6f 6b 69 65 6d 65 61 74 b1 42`.

The protocol still requires two matching valid frames, so roughly 23.5 seconds from first usable signal is expected for this WAV. D07 has not yet been tested on the physical phone; automated repeatability does not establish repeatability in the room.
